=== Setup: primary localhost:27018, up-to-date secondary localhost:27019, delayed secondary localhost:27020
The delayed member applies changes 20 seconds late, like a copy at a second site on a slow link

##### PART 1: a write confirmed by the primary alone (w: 1), then read from each copy
{
  seconds_after_write: 2,
  primary_has_it: true,
  up_to_date_secondary_has_it: true,
  delayed_secondary_has_it: false
}
A doctor reading from the delayed copy would see the old record: a stale read.

Waiting 25 seconds...
{
  seconds_after_write: 27,
  primary_has_it: true,
  up_to_date_secondary_has_it: true,
  delayed_secondary_has_it: true
}
All three copies now agree: the data is eventually consistent.

##### PART 2: how many members must confirm a write before the application carries on
{
  write_concern: 'majority (2 of 3)',
  result: 'confirmed',
  milliseconds: 11
}
{
  write_concern: 'all 3',
  result: 'timed out',
  milliseconds: 5031,
  error: 'waiting for replication timed out'
}
{
  reading_is_on_the_primary_anyway: true
}
The write was not undone: the timeout only means the application could not be told that every copy had it.
